# Runtime and integration testcase audit

This supplements the [CI testcase audit](ci-testcase-audit.md) and
[testing strategy](testing-strategy.md). It examines 60 current or retired cases
from `mcp-model-reasoning` through `workflow-resume-restart-recovery` in the
2026-10-18 consolidation inventory, including their implementations and
assertion helpers. The comparison baseline is
`1c629c80b383d7e53e01f266430d0fa41c5d9bf6`.

This slice now contains **54 cases selected by at least one profile and six
retired cases**, with no unreachable registration. A profile assignment describes reachability, not proof
that a particular PR executed it. This is a source audit, not a report of new
cluster runs. Profile selection remains owned by
[testmatrix](../../../e2e/pkg/testmatrix/testcases.go), profile `GetTestCases`
methods and the runtime inventory command documented in the main audit.

## How to interpret the findings

The [registration wrapper](../../../e2e/pkg/testcases/registry.go) applies
[acceptance contracts](../../../e2e/pkg/testcases/acceptance_contracts.go)
only to explicitly named cases and profiles. None of the 60 names below gets
the baseline `envoy-ai-gateway` percentage floors. In particular,
`routing-fallback` is different from `decision-fallback-behavior`. A metric in
`SetDetails`, a description or a printed percentage does not add a failure
condition by itself.

**Keep** means retain the assertion in its affected integration family and
share setup where safe; it does not justify a separate job for every row.
**Repair** identifies missing acceptance evidence. **Downgrade** narrows the
claim to what the implementation actually proves. **Retired** means the
harness and its exclusive fixtures were removed. Five retired names were
unreachable and never consumed CI runtime; removing the selected
`routing-fallback` aggregate removes 20 requests when its profile runs, while
retaining the profile and its job. Useful current behavior is checked by direct
module tests and the retained routed controls within their stated boundaries.

The most consequential gaps in this slice are:

- The retired `routing-fallback` aggregate accepted one correct category;
  method and confidence were diagnostic, and missing method evidence could be
  inferred from the expected fixture. It never qualified the claimed fallback
  chain. Current decision-ordering tests and provider failover controls remain,
  without claiming that either proves the legacy classifier-backend sequence.
- `model-selection` still checks a 75% decision/model-membership rate, not
  algorithm identity or efficiency. Its loader and the shared signal loader now
  require nonempty checked-in corpora: missing, malformed, empty-array and null
  inputs fail closed. Preference and structure retain their existing positive
  and negative probes; the loader does not require both fixture types.
- `performance-throughput` has request-success checks but no throughput or
  percentile budget. `resource-utilization-monitoring` accepts any nonempty
  namespace CPU query result. Neither is a performance regression gate.
- The three retired MCP cases accepted a single successful probe, and the
  probability case did not require valid probability evidence. Direct HTTP
  and stdio transport tests now preserve payload and error contracts without
  pretending that server metadata controls Router decision selection.

## Consolidation consequences

Retain distinct positive, negative and recovery assertions while batching
compatible profiles on a small number of workers. In particular, model-runtime
kill/retry cases, shadow queue controls and standalone configuration rollout
mutate their fixtures and must remain ordered or isolated. Deleting these
assertions to reduce job count would remove useful behavioral evidence.

Conversely, telemetry availability, replica readiness, sequential request smoke
and direct provider-fixture checks do not warrant independent expensive jobs.
Run them beside the stack or protocol coverage that already pays for their
setup, and label the result by its actual contract. Keep real-model and
performance qualification explicit in the scope/receipt model described in the
testing strategy. Do not use an unselected debt case, a printed benchmark or a
weak aggregate to satisfy a required verification.
