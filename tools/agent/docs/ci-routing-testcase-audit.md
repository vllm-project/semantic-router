# Routing and integration testcase audit

This companion to the [CI testcase audit](ci-testcase-audit.md) records a
2026-10-18 implementation review of 63 additional current or retired cases, from
`agentgateway-full-duplex-multiturn` through `mcp-http-classification` in the
expanded runtime inventory. The review follows request helpers, result
aggregation, fixtures and acceptance wrappers; a test's name is not its oracle.

Before cleanup, 51 of these names were selected by a registered profile and
12 had no selecting profile. Retiring three report-only Dynamo cases, all
12 unreachable cases, three weak routing aggregates, and ten external-integration
cases leaves **35 selected registrations and 28 retired cases**, with no unreachable registration in this
slice. A selecting profile does not establish that a particular CI run executes it. The [verification catalog](../../ci/verification_catalog.py)
and execution plan determine scheduling. In particular, a GPU deployment profile
is not evidence of GPU coverage on hosted CPU runners. Dynamo and the
agentgateway, AIBrix, Istio and llm-d profiles are retired.
Their deployment examples have no maintained E2E or manual CI qualification.

The [registry](../../../e2e/pkg/testcases/registry.go#L99) wraps functions with
[profile-scoped acceptance](../../../e2e/pkg/testcases/acceptance_contracts.go#L111).
Those additional thresholds apply only to the named baseline cases in
`envoy-ai-gateway`; **none of the 63 cases here has that additional gate**.
Report fields and log messages therefore count as assertions only when the
case or its helpers use them to return an error. Existing baseline model-quality
and stress acceptance floors remain separate and unchanged.

## Findings that affect qualification

- Three Dynamo cases had no useful pass/fail oracle: all five concurrent
  requests could fail, all ten benchmark responses could be HTTP 500, or worker
  discovery could fail, respectively, without failing their case. They are
  retired, including registration and profile selection. Historical source
  links below use baseline `1c629c80b383d7e53e01f266430d0fa41c5d9bf6`.
- Text embedding, entropy and keyword routing aggregates are retired with
  their exclusive fixtures. Their 69 requests needed only one matching result
  per aggregate; missing reasoning evidence could count as `false`. Existing
  direct tests enforce algorithm boundaries, while retained routed controls
  enforce selected deployment wiring. These are narrower, explicit claims,
  not equivalent semantic-quality coverage of all retired prompts. Neither
  containing profile is removed, so this change saves probes when selected,
  not job allocations.
- The production failover test now requires pod discovery and successful
  deletion before applying its unchanged availability and recovery floors.
  Local API failure controls prevent skipped disruption from passing. The load
  test checks availability with two configured endpoints, not distribution
  across them.
- Twelve unreachable names in this slice are retired: nine old selectors,
  one superseded authorization case and two MCP cases. They never ran in CI,
  so this removes maintenance debt without claiming runner-time savings.
  Current selector, learning API and trusted-identity tests preserve the
  useful behavior directly; obsolete algorithms and deleted API routes are
  not kept alive by historical test names.

Recommendations below distinguish retaining semantic cases from sharing their
cluster/job setup. “Keep” does not require one job per case. “Consolidate” means
share compatible setup or replace overlapping smoke assertions; it does not
mean dropping distinct negative controls. Items marked “repair” are findings,
not claims that this change implements those repairs.

## Looper cases

resets backend counters, requires successful reset/read HTTP responses and checks
exact dispatch counts. These counters are global to the fake backend: preserve
sequential case execution when sharing a job. Missing counter keys count as zero,
so error-path cases that only require zero dispatches still need their other
assertions to establish that the intended branch ran.
