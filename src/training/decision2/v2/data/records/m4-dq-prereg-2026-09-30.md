## 3. PN1 (c): blind label review of TRAIN

### 3.1 Sample

- **Population:** `pn1.train.jsonl`.
- **Cells:** language (8) × construction group (natural = `pn-hop` + `pn-near`; swap = `pn-name` + `pn-twin`)
  × gold label (yes / no). es and fr have no swap rows, so there are 14 language × group cells and 28 cells
  with the label.
- **Allocation:** 8 rows per cell, **224 rows**. Every cell has at least 10 rows.
- **Order:** rows in `sha256("dq-pn1-review-v1:" + id)` order; a row is taken while its cell has fewer than 8
  and its `group_id` is not taken yet (at most one row per group). A cell that runs short keeps what it gets,
  and that is reported.

### 3.2 Blind packets

- Each item carries only what the model sees: the language name, the row's `instructions`, its `state` (the
  two sentences in the row's English layout) and the option descriptions (`["No", "Yes"]`). It has an opaque
  review id `pNNN`, assigned in `sha256("dq-pn1-packet-v1:" + id)` order.
- Removed: row id, group, family, label, source, render template and all audit metadata (judge scores, edit
  info, Tatoeba ids). The builder checks that no row id, group id or family name occurs in a packet.
- The key (review id → row id, cell, family, gold, judge probability) is written only on node A, and only
  reaches this machine after every blind answer is in.

### 3.3 Reviewers

- Internal subagents (Claude, model `claude-opus-5-5-max`), started fresh, with the committed instructions
  [`dq/reviewer-pn1.md`](dq/reviewer-pn1.md). They are told to read only their packet file, and they have
  no gold. They answer yes / no, give a confidence, rate each sentence's fluency, and add a short note.
- **R1 and R2** each review all 224 items independently, in different orders (R2 in
  `sha256("dq-pn1-r2-order-v1:" + rid)` order).
- **R3**, a fresh subagent, reviews only the items where R1 and R2 split (instructions
  [`dq/adjudicator.md`](dq/adjudicator.md) part 1). It is not told why the items were chosen.
- **Gold error:** the majority of the blind answers differs from the gold. That means both R1 and R2 disagree
  with the gold, or they split and R3 disagrees with it.
- Limitation, disclosed: all reviewers are the same model family, so their errors may correlate. This is
  AI adjudication, not human annotation.

### 3.4 Measures (all with 95% intervals)

- **Label error rate,** pooled over the 224 rows: Clopper–Pearson (exact) and Wilson intervals.
- **Population-weighted error:** cell weights = TRAIN cell share / sample cell share; percentile interval from a
  stratified bootstrap (10,000 resamples, within cells, fixed seed).
- **Agreement with gold** for R1, R2 and the majority (Wilson), and R3 on the splits.
- **Inter-reviewer agreement:** raw agreement and Cohen's κ (stratified-bootstrap interval).
- **Breakdowns** by language, construction group, gold label, family and language × group, with exact
  intervals.
- **Direction:** false yes versus false no.
- **Fluency:** the share of swap rows whose edited sentence both R1 and R2 call ungrammatical. Reported, not
  gating.

### 3.5 Pass thresholds (fixed now, before any answer is seen)

PN1 passes iff all of these hold:

- **P1:** the pooled label error is ≤ 5.0% **and** its exact 95% upper bound is ≤ 8.0% (so at most 9 errors
  of 224).
- **P2:** the population-weighted error is ≤ 5.0% (point estimate).
- **P3:** no language × group cell (16 rows) has ≥ 4 errors. At 4 of 16 the exact lower bound first exceeds
  5%.

### 3.6 Fix rule if PN1 fails

The fix rule is applied once, in this order, then the verdict is re-evaluated. There is no further iteration.

- **F2:** every language × group cell that fails P3 is dropped from TRAIN.
- **Re-evaluation:** P1 and P2 are recomputed on the reviewed rows of the remaining cells, with population
  weights over the remaining cells.
- **F3:** if P1 or P2 still fails, the judge-margin filter is applied to the remaining TRAIN. A yes row stays
  only if its recorded judge `label_p_yes` ≥ 0.80, and a no row only if it is ≤ 0.20. Rows without a recorded
  judge probability stay. P1 and P2 are then recomputed on the reviewed rows that survive F3.
- **F1:** whenever the arm is republished for any reason (this rule or §1 / §2), the rows the review judged to
  be gold errors are dropped too.
- **F0:** groups dropped by §1 or §2 are removed before re-evaluation.
- **Balance repair:** labels are restored to exactly 50/50 in every language × group cell. Surplus rows of the
  larger label are dropped in `sha256("dq-pn1-balance-v1:" + id)` order, taking reviewed rows only if nothing
  else is left.
- **Re-evaluation uses review-independent survivors only.** It counts the reviewed rows that survive F0, F2
  and F3. F1 is not used for it, because F1 is chosen by the review itself.
- **Outcome:** FIXED-PASS means re-freeze the fixed TRAIN (`v2.data.freeze`), re-run the A4 overlap learner
  (reported), then run `hf_headroom.sh` and upload `m4/pn1/arms/pn1.train.jsonl` and the manifests as a
  **new revision** of the private dataset, with a read-back SHA-256 check. The new hashes are recorded here and
  in gist 02.
  - If the verdict is still FAIL, PN1 stays **not release-safe**, is flagged in the records, and is not tuned
    further.
- **On PASS:** no republish. The rows judged wrong are listed by id in the private report and counted in the
  record.

## 4. HS1 spot-check (template check)

- **Sample:** `hs1.train.jsonl`. **17 rows per family × task type** (Choice / Noul / Score), which is **51
  per family and 153 in total**. Rows are taken in `sha256("dq-hs1-spot-v1:" + id)` order, at most one per
  group (world).
- **Blind packets:** `task_type`, `instructions`, `state`, and options with keys. They carry an opaque id
  `hNNN` in `sha256("dq-hs1-packet-v1:" + id)` order. Gold, family, kind, template, ids and audit metadata are
  removed.
- **Reviewers:** one fresh blind subagent per packet, with [`dq/reviewer-hs1.md`](dq/reviewer-hs1.md). F1 and
  F3 go to one reviewer and F2 (the long packets) to another. Each answers every item and flags
  rendering / contradiction / ambiguity / option defects.
- **Adjudication (blind):** every row whose answer differs from the gold, and every flagged row, goes to a
  fresh subagent with [`dq/adjudicator.md`](dq/adjudicator.md) part 2.
  - Disagreements come as two unlabelled candidates, A and B, in a salted order (one is the gold). The verdict
    is A, B, both or neither.
  - Flags come as the reported issue. The verdict is defect or no defect.
- **Candidate defect:** the adjudicator does not pick the gold (B, both or neither), or confirms a flagged
  defect.
- **Root cause (worker, after adjudication):** each candidate defect is traced in the generator code and in the
  row's facts and audit metadata.
  - **Confirmed defect:** a reproducible template cause, a rendering bug or an ambiguity by construction. Its
    cause is written in the record.
  - **Not confirmed:** the state determines the gold. The derivation from the text is written in the record,
    and the item is counted as a reviewer error.
- **Measures:** per family, reviewer agreement with gold (Wilson), candidate and confirmed defect rates (exact
  intervals); the same pooled.
- **Pass rule:** HS1 passes iff **no defect is confirmed**. With 51 rows per family, a clean result bounds each
  family's defect rate below 7.0% at 95% (exact).
- **If defects are confirmed:** fix the template(s) in `v2/data/hs1/`, rebuild with the house build and
  re-check, and re-run the HS1 audits (balance, shortcut probes, overlap / structural scans, isolation). Then
  republish `m4/hs1/` as a new revision after `hf_headroom.sh`, with a read-back SHA-256 check, and record the
  new hashes. Otherwise nothing changes.

## 5. Qualification-pool relabel

- **Why:** the AutoJev-27B runtime-qualification sets (M3a, `v2/data/m3/qualify.py`) hold the spot-check set
  S, which contains 128 typed FINAL prompts, plus 231 public-231 and 128 CSS15 prompts. Their outputs were never
  targets. The training-corpora manifest (`training-corpora.json`, `cbf8a731…`) still lists three copies under
  training labels (`local-m3a`, `local-m3a2`, `r2-local`).
- **Registry:** a committed evaluation-only registry lists these pools by path pattern (the `qual/` trees of
  the M3a work directories and their copies) and by file SHA-256. Evaluation panels have no business in a
  mixture either, so the registry also lists the installed gold-free panel prompt files.
- **Relabel:** a relabelled copy of the manifest is written on node A as a new file (the old one stays, since
  its hash is cited). The matching files move into sibling labels with `"kind": "evaluation-only"`, and every
  other file keeps its training label. The new hash is recorded. The manifest writer
  (`v2.eval.htdev_iso.manifest`) applies the same registry to future manifests. That is a small shared-module
  change, made in its own commit with a test.
- **Guard:** mixture builders refuse the registry's pools. A path or file-hash match, or a row whose id is a
  qualification spot-check id, raises before anything is written. There is a test for the guard and a test
  that every mixture builder module calls it.
