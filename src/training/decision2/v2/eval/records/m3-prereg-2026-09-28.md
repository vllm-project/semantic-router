## M3.1 Option-key / position leak audit (CPU, first)

**Why.** A7 found that Decision 1.0 builders numbered Choice keys `result_<n>` in
construction order and shuffled the options afterwards, so the key number revealed the
gold (7,579/7,579 intent rows). The data track found the same class of bug in rotated
keys (`o1..oN` in source order). 1.0-lineage models trained on such rows may exploit the
same surface on panels built by the same generators.

**Panels (all eight, hash-verified by `v2.eval.panels verify`).** Development: SELECT,
CAL, typed DEV, CSS pilot, mlx-diag. Formal: typed FINAL, CSS15 (v3 human transfer),
JevBench public 231.

**Method (`v2/eval/leak_audit.py`).** Every question becomes options in display order
plus the gold index. Cues of the A7 kind (option surface): display position; the token of
a non-semantic key (numbered, letter or opaque); key-number rank among numbered keys;
lexicographic key rank; key scheme; description length rank; description whitespace;
shared versus unique description; key or description mentioned in the instructions.
Typed panels also get a state-surface cue, reported separately: the option entity's slot
in the state lists or its top-level state role. The label prior is the cross-validated
gold frequency of the description and of semantic keys (words, true/false/none, Score
levels). Each cue is scored alone and added to the prior; a naive-Bayes combination of
all option-surface cues (then plus the state cue) with the prior gives the headline
gain. 5-fold CV with folds by source group (typed `group_id`, SELECT/CAL `group_id`,
mlx-diag source item, public 231 `group`, otherwise the item). Cluster bootstrap,
2,000 replicates, seed 20260928. Deterministic checks: `result_<n>` rows, numbered keys
out of display order (the A7 signature) with the gold key rank, distinct option orders,
gold position counts, item ids that contain the gold key.

**Verdict rule (per group and per panel x type).** LEAK: gain over the prior ≥ 5 points
and 95% interval above 0. CUE: interval above 0, gain below 5 points. CLEAN otherwise.
About 60 groups are tested, so roughly one or two CUE verdicts are expected by chance;
a CUE counts only if it replicates on the sibling panel (SELECT↔CAL, DEV↔FINAL) or in
the pooled row.

**Actions.**

- Development or calibration panel with LEAK: publish a corrected version (keys
  renumbered by display position with `v2/common/option_keys.py` semantics, or options
  reordered by a salted hash), new hashes in `panels.py` as a new panel name (the old
  name keeps its hash), re-score stored predictions where the prompt change does not
  alter the answer space, and recalibrate the development proxy and tie rule on the
  corrected panels.
- Formal panel with LEAK: the formal panel is not changed. From stored predictions,
  report per model the accuracy on cue-consistent versus cue-inconsistent items and the
  cue-following rate, and propose a disclosed correction (for example a leak-neutral
  slice score) to the coordinator.
- CUE or CLEAN: record, no change.

Receipts hold counts and accuracies only (no item text, no gold values).
