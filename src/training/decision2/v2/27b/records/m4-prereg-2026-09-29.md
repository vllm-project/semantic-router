## Question

F1 trails AutoJev-27B by −4.92 v3 (−6.82, −0.43), almost all of it typed accuracy T (−.099), and
within T two unseen formal families: constraint competition .570 vs 1.000 and exception stack .788 vs
.843. M3's matched control credited about 5M A7 Stage 1–4 tokens with ΔT +.099 (+.081, +.118).

1. **Dose / content:** does a four-times-larger A7 slice (20M tokens) raise typed reasoning on the
   unseen formal families more than repeating M3-A's own mixture to the same number of tokens?
2. **Capacity:** at that dose, does a rank-32 adapter do better than rank 8?
3. **Release:** does any arm soup beat F1 on post-key v3 (paired lower bound > 0) without losing
   human transfer?

- **Why this placement.** Soups and formal runs happen on node B, and node A checkpoints reach it
  only through the workstation, at 0.13–0.22 MB/s (measured 16:25 UTC+8).
  - A rank-8 BEST checkpoint needs about 0.25 GB (adapter 234 MB FP32 plus head and configs), about
    30 minutes.
  - A rank-32 one needs about 0.95 GB, about 1.5 hours.

  So both rank-32 seeds train on node B, and the three node A runs are rank 8.
- **Node confounding.** A20 has one seed on each node, A20r trains only on node B, and Ar has one
  node B seed and one node A seed. Same image, base bytes, code and T0 cache leave no known source of
  a systematic node effect; the cross-node probe tests step-1 equality.
- **Relays.** Node A's three BEST checkpoints (without `trainer_state.pt`) are streamed to node B as
  each run completes. They are checked by per-file SHA-256 on both sides before any soup.

## Preflights and stop rules (per arm-seed)

- **Preflights:** admission (every row of the mixture admitted at 4,096), one-step, reload (32
  SELECT rows, 0 argmax changes, max |Δp| ≤ 1e-4).
  - **A preflight failure is recorded and stops that arm, both seeds.** A sibling that is already
    running is stopped and recorded. Nothing is rerun, and the arm gets no soup or formal run.
- **Caps:**
  - 13.0 GPU-hours cumulative per arm-seed: preflights, the full attempt and any recovery. Each full
    launch is capped at what is left.
  - One attempt per arm-seed. A cap hit, a nonfinite loss or an OOM stops the arm-seed; it is
    recorded and not rerun, and its arm gets no soup.
  - Exit 139 (native runtime fault) keeps M3's rule: at most two exact recoveries from the latest
    complete checkpoint, inside the same 13-hour cap. This is an interruption, not a new attempt.
- **Milestone cap: 70 GPU-hours** (wall-clock × GPUs, preflights and evaluation included).
  - **G1, a projection check** after about 300 full-training updates of every run, from the logged
    seconds per update (`m4-status.sh`):
    - if projected training plus the 2.7 GPU-hour evaluation plan fits in 70, continue as planned;
    - if it fits only without the optional evaluation items (CAL698 fits 0.15 and mlx-diag 0.36, so
      training plus 2.1), continue and run those items only while the running total leaves room for
      every remaining formal run;
    - otherwise stop M4-A20r (both seeds) at once and record a budget stop; the capacity contrast is
      then not run.
  - **Running-total check** before every post-training GPU stage: no stage starts if it would pass
    70. The order is soup readouts, CAL698 fits, formal runs, then mlx-diag.

## Soups, readouts and finalists

- **Soups:** for each arm, the exact uniform soup of its two seeds' BEST checkpoints (`lora_soup.py`
  via `run_finalist.sh STAGES=soup`).
  - LoRA factors are concatenated along the rank: A′ = [A₁; A₂], B′ = [B₁, B₂] / 2, with r′ = 2r and
    α′ = 2α. The decision head is averaged.
  - Verified on every projection: max |ΔW_soup − mean ΔW_seeds| ≤ 1e-6 × max |mean ΔW_seeds| (FP32).
    The release builder's adapter checks must pass.
  - **The candidate artifact of every arm is its soup** (condition 4). The 17:15 seed rule is not
    used, and no per-seed kernel readout is taken, to save budget. Per-seed SELECT700 at BEST comes
    from the trainer.
- **Soup readouts, which serve only as sanity guards.** On node B, kernel path, 32,768 tokens, and a
  fresh copy of `583241fb`: typed DEV and CSS pilot, SELECT700 and CAL698 kernel-path probabilities,
  `v2.eval.dev_readout`, P_dev = 100·√(T_dev·H_pilot).
  - **Collapse check:** a soup does not go to the formal runner if its typed DEV shows any type at or
    below chance (Choice .267 / Noul .50 / Score .20, the formal gate's levels), or one answer
    category for a whole type, or invalid answers above 1% on typed DEV or the CSS pilot.
  - **Proxy-drop rule (proxy v2):** a soup is dropped if its P_dev is at least 8 below the best of
    F1's P_dev (77.03, read on the same path, limit and cache) and the three M4 soups.
  - Everything else goes to the formal runner, at most three finalists.
  - Retention against F1 is report-only: a typed-DEV type down more than 3 points, H_pilot down more
    than 1.5, CAL698 Brier worse by more than 0.010, or more invalid answers.
- **Calibration (23:15 rule):** CAL698 temperatures are fitted at 32,768 on the kernel path
  (`calibrate_frozen.py`). They are ADOPTED only if they do not worsen aggregate ECE and Brier on
  typed DEV and the CSS pilot (`dev_calibration.py`), decided before the formal collection;
  otherwise T = 1. The package (checkpoint, adopted calibration, limit) is frozen before its formal
  collection.
- **Formal run (post-key same-panel):** node B, image `dbe5f32b`, a fresh verified copy of F1's
  scored cache `03b172f1…`, an 8-item smoke per panel, then typed FINAL, CSS15 and public231. Then
  seal and report. The post-run cache check is recorded.

- **Successor rule (coordinator condition 4, declared now).** An arm soup replaces F1 only if all of
  these hold:
  1. its post-key v3 minus F1 has a paired 95% CI lower bound > 0;
  2. its human transfer is not significantly below F1's (the paired ΔH CI includes 0 or lies above
     it);
  3. every no-1.0 gate holds:
     - v3 ≥ 64.92;
     - human transfer not significantly below AutoJev-27B, Eikos-27B or Jebadiah-27B;
     - no type collapsed: every type above chance on typed FINAL, with more than one answer category

  point estimate, then the smaller adapter (rank 16 before rank 64).

  coordinator for a release step, and nothing goes to Hugging Face during the milestone.
- **Attribution, declared up front** (paired 95% CIs on T, v3, H and the four FINAL families):
  - **content / dose at matched tokens** = M4-A20 − M4-Ar. "New A7 content beats repeating M3-A's
    rows" is claimed only if the lower bound of ΔT is above 0. The type-mix difference above is
    disclosed with it.
  - **capacity** = M4-A20r − M4-A20. "Rank 32 adds typed reasoning at this dose" is claimed only if
    the lower bound of ΔT is above 0.
  - **Descriptive:** M4-A20 − F1 (dose 20M vs 5M, 2.5× the tokens) and M4-Ar − F1 (more updates on
    the same rows).
- **mlx-diag (coordinator-ordered diagnostic, never a release score).** Every finalist is collected

## Budget (GPU-hours = wall-clock × GPUs)

M3's receipts give about 10.0 s per update at 6.2k tokens per update (M3-A) and 10.5 s at 7.3k
(M3-S). A fixed per-row cost dominates, so the cost follows updates more than tokens.

| Item | GPU-h |
| --- | ---: |
| M4-A20 × 2 (3,561 updates at ≈ 10.4 s; preflights 0.1) | 2 × 10.35 |
| M4-A20r × 2 (rank-32 overhead assumed ≈ 2%) | 2 × 10.56 |
| M4-Ar × 2 (2.494 × M3-A's mean full attempt 4.49; preflights 0.1) | 2 × 11.29 |
| Cross-node probe | 0.08 |
| 3 soup readouts (0.25), 3 CAL698 fits (0.05), 3 formal runs (0.45) | 2.25 |
| mlx-diag: 3 collections + 1 smoke | 0.36 |
| **Planned total** | **≈ 67.1** (cap 70; per arm-seed cap 13) |

The proposal's ≈ 63 GPU-hours for training assumed 2.4M tokens per GPU-hour. The a20 rows are longer
than M3-A's, which helps, but Ar repeats M3-A's shorter rows (≈ 2.2M tokens per GPU-hour), so the
margin is about 2.9 GPU-hours. G1 guards it.

## Chain rule, heartbeats and handoff

- Every driver runs from the verified mirror. Before each launch, its size and SHA-256 are compared
  with this commit's blob, and the check is recorded.
- Each launch is its own ssh call: `setsid nohup … < /dev/null`, output to a log.
- **Liveness is checked by container name** (`d2-27b-<ARM>-<stage>` in `docker ps`) and by the first
  log lines, never by a `pgrep -f` pattern that can match the checking shell.
- **Heartbeats:** `m4-status.sh NODE --loop 600` on each node rewrites
  `/data/dev2/runs/27b/m4-logs/heartbeat-<node>.json`.
- `m4-state.md` is updated after every step, so a successor worker can take over.
- Records: this file (amendments appended), `m4-results-2026-09-29.md`, `m4-state.md`, gist 06.
