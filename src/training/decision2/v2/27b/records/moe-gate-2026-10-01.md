## Software support on the pinned image `dbe5f32b` (CPU checks)

- torch 2.12.0+git6bbd260 (HIP 7.2.53211), Transformers 5.17.0, PEFT 0.21.0, FLA 0.5.2, causal-conv1d 1.7.0,
  accelerate 1.15.0. `torch._grouped_mm` exists.
- `Gemma4ForConditionalGeneration` and `Qwen3_5MoeForConditionalGeneration` are in Transformers 5.17. Both expert
  classes use `@use_experts_implementation`: `from_pretrained(..., experts_implementation=...)` selects `eager`,
  `grouped_mm` (the default, falling back to eager), `batched_mm`, `deepgemm` or `sonicmoe`. The GPU parity / speed
  probe pins one per family before training.
- Qwen3.5-MoE's GDN layers are the Qwen3.5 gated-delta blocks: the FLA / causal-conv1d kernel path and the persisted
  Triton autotune cache apply as for the dense 27B. Gemma has no gated-delta layers (SDPA only).
- PEFT 0.21 supports `target_parameters` (LoRA on the 3-D expert tensors). This milestone keeps experts frozen (below).

## Memory on MI325X (256 GB per GPU)

- **LoRA (the house precision: FP32 parameters, BF16 autocast, gradient checkpointing, one GPU):** Gemma ≈ 101 GB of
  FP32 weights (M1 measured 101.0 / 103.1 GB resident / peak for a forward), Qwen3.5-MoE ≈ 139–144 GB, plus
  activations for ≤ 4,736-token rows. Both fit one GPU; the probe records the peak.
- **Full fine-tuning (FP32 AdamW, 16 B/parameter, FSDP):** Gemma ≈ 404 GB → ≈ 135 GB per GPU on node A's three GPUs
  plus activations (M4b's 25.6B dense peaked at ≈ 175 GB per GPU): feasible on node A only. Qwen3.5-MoE ≈ 555 GB →
  ≈ 185 GB per GPU on three GPUs plus activations: marginal; not feasible on node B's two GPUs.
- **Choice, by evidence: LoRA, not full fine-tuning.** Full fine-tuning on the A20 mixture overfit typed families and
  cost human transfer (M5-FF20: HT-DEV v2 −.049 [−.070, −.029] vs A20r), while the rank-32 LoRA recipe (A20r) is the
  released best. Full fine-tuning is not run in this milestone.

## Decision-model support (what each backbone needs, and what was implemented)

- **Loading:** the text decoder `model.language_model` of each official multimodal checkpoint (vision tower loaded but
  unused), FP32, SDPA, the pinned experts implementation, strict loading (no missing / mismatched keys).
- **Readout:** `CandidateHead` is unchanged: option endpoint vectors and the final query vector from
  `last_hidden_state` (post-norm). The segmented renderer is unchanged.
- **Prompt:** Gemma is trained and served behind its BOS token (new prompt version
  `decision2-bos-segmented-options-global-query-v1`, every endpoint shifted by one); Qwen needs none.
- **LoRA targets (experts and routers frozen):** every layer's attention (`q/k/v/o`; Gemma's global layers have no
  `v_proj`) or gated-delta projections (`in_proj_qkv/z/b/a`, `out_proj`), plus Gemma's dense MLP
  (`gate/up/down_proj`) or Qwen's shared expert (`gate/up/down_proj`). No target lives under `experts`, `router` or
  `mlp.gate`; the shared-expert gate stays frozen.
- **Implemented** (tests in the image: 84 `training/model` tests + 4 new MoE tests + 2 pipeline tests pass):
  - shared modules `training/model/{decision_model,lora,infer,calibrate}.py` (separate commit): `from_moe_base`,
    `encode_bos` / `encoder_for`, `moe_summary`, the MoE LoRA selector; dense paths unchanged;
  - the training pipeline `v2/27b/moe/pinned/moe-pipeline-2026-10-01.tar` = the BEST368 pipeline that trained A20r
    plus the same patch (5 files changed, 7 byte-identical; `moe-pipeline-2026-10-01.patch`); a test shows dense
    Qwen3.5 targets and prompts equal BEST368's;
  - MoE drivers: `moe/launch.py` (the 27B launcher with this milestone's GPUs and lease track `27b-moe`),
    `moe/moe-arm.sh`, `moe/preflight_reload.py`, `moe/experts_probe.py`.
- Full-weight MoE checkpoints are refused by the loaders (not needed: LoRA only).
