The standalone Router builds and runs on a SpacemiT X60 RISC-V server. On openKylin 2.0 SP1, the container passed eight routing and restart checks. With a two-CPU limit and concurrency 4–64, it handled about **270–280 requests/s** in a short keyword/default-routing workload.

This work is part of OSPP project [2647b0097, 面向多架构环境的 vLLM Semantic Router 运行支持](https://summer.ospp.ac.cn/org/prodetail/2647b0097?lang=zh&list=pro). It covers the Go Router and its container build. Model inference remains external. The port is proposed in [PR #5259](https://github.com/vllm-project/semantic-router/pull/5259), with experimental platform status.

## What runs on RISC-V

In standalone mode, the Router accepts HTTP requests and forwards them to the model API selected by its routing policy. It can also call an external classification service. The keyword and default policies tested here do not need a classifier.

## The build changes

### Building GLIDE from source

The first build blocker was GLIDE. Its Go client links to a Rust FFI library, and the v2.3.0 module used by the Router does not include the required RISC-V archive. Turning off Valkey-backed features in configuration still leaves that link dependency.

The build compiles GLIDE's `ffi` crate for `riscv64gc-unknown-linux-gnu` and links `libglide_ffi.a` into the Go binary. It checks the source archive's SHA256 and verifies the resulting archive's ELF architecture. A Cargo lock pins Rust dependencies because the v2.3.0 source archive does not include `ffi/Cargo.lock`.

We have requested upstream support in [Valkey GLIDE #7388](https://github.com/valkey-io/valkey-glide/issues/7388).

### Separating the image build

`tools/docker/riscv64/Dockerfile` compiles GLIDE and exports the Go binary in a small intermediate image. The independent `tools/docker/Dockerfile.attached` accepts that binary image and packages the Router, configuration assets and startup script without bundled PyTorch or `vllm-srun`. It can also build the standard amd64/arm64 binary itself.

The port leaves the bundled `Dockerfile.extproc` unchanged. The proposal registers a separate [`vllm-sr-riscv64` artifact](https://github.com/LeON-Nie-code/semantic-router/blob/2e89999771dc3bb2458e1bc86ef00c4e918dd591/tools/ci/image_artifacts.py#L28), keeping the existing CPU/CUDA/ROCm image definitions intact.

## Build it on a RISC-V host

The SDK pins Go 1.25.14 and Rust 1.90.0 archives by URL and SHA256, and the Debian base by digest.

From the repository root on a native RISC-V64 Linux host with Python 3.10+ and Docker/buildx:

```bash
python3 tools/docker/riscv64/build.py --plan
python3 tools/docker/riscv64/build.py --tag local \
  --output /tmp/vsr-riscv-build
```

This produces the SDK, native binary image and `semantic-router-router:local` runtime image. Use a new output directory for each run; it records the commands and build results. The Docker buildx `docker` driver is required to pass local images between stages. The host needs network access to the image, toolchain and dependency repositories.

The runner accepts `--sdk-image` to reuse an SDK and `--no-cache` for fresh-layer builds. This validation reused the SDK and cached layers.

## Native container validation

The test host was a SpacemiT X60 with 8 cores and 16 GB RAM, running openKylin 2.0 SP1 and kernel `6.6.63-cloud`. Compilation and container execution ran natively on the server. The Router ran as a non-root user with a read-only root filesystem.

## HTTP workload results

We compared the X60 deployment with an AMD Ryzen 9 9950X host, using the same Router revision and the same Go benchmark source compiled natively for each architecture. The performance backend returned a fixed OpenAI-compatible JSON response; no LLM generation or classifier inference was involved.

| Setting | RISC-V | x86 |
| --- | --- | --- |
| CPU | SpacemiT X60, 8 cores, 16 GB RAM | AMD Ryzen 9 9950X, 16 cores / 32 threads |
| Host OS/kernel | openKylin 2.0 SP1 / `6.6.63-cloud` | Linux / `6.8.0-147-generic` |
| Router limits | 2 CPUs, 1 GiB, `GOMAXPROCS=2` | Same |
| Router logging | `SR_LOG_LEVEL=warn` | Same |
| Client and backend | Separate native Go processes, each `GOMAXPROCS=2`; built with Go 1.25.14 | Same |
| Test | Concurrency 1, 4, 16, 64; 15 seconds per path; 3 repeats | Same |

Each host ran two loopback paths: directly to a fixed-response Go backend, and through the Router to that backend. Workers alternated two short prompts, checked the returned model and `ok` content, and waited for each response before sending the next request. The client used an HTTP/1.1 connection pool and prepared request bodies before timing. Responses were buffered (`stream: false`); SSE was tested separately above.

Both hosts passed all **24 phases with zero request errors**. X60 completed 42,897 timed requests through the Router; x86 completed 1,556,699. The table gives the median of three phase results, with warmups excluded. The p50 and p95 columns are medians of phase percentiles.

### Where throughput levels off

At concurrency 4 and above, X60 sustained about 270–280 requests/s and x86 about 10,000–11,000. More concurrent requests increased latency without increasing throughput. Direct-backend throughput was about 10–12 times the routed throughput on X60 and 12–16 times on x86.

[![CPU use at concurrency 16 for the load generator, fixed-response backend and Router on both hosts.](/img/blog/ospp-riscv64/cpu-en.png)](/img/blog/ospp-riscv64/cpu-en.png)

*Average CPU cores used at concurrency 16, taking the median of three runs. Both Router containers had a two-CPU quota.*

The X60 Router used 1.97 CPU cores, versus 0.43 for the client and 0.33 for the backend. On x86, the Router used 1.99 cores. The load generator and backend had room to spare on both hosts, while the Router approached its two-CPU allowance. The measured path includes HTTP handling, routing, forwarding and response processing.

<details>
<summary>Measurement details and variation</summary>

- Each path received 20 warmup requests, with another warmup attempt per worker before each phase. Path order alternated between repeats. This was a closed-loop test; actual connection reuse was not counted.
- Client and backend processes were outside the Router's CPU quota but shared its host. Other workloads remained running, without CPU pinning. One-minute load averages changed from 2.20 to 5.68 on X60 and from 0.15 to 5.92 on x86.
- Across both paths, X60 completed 504,194 timed requests and x86 22,913,211. Latency quantiles were computed per phase, not from pooled samples.
- CPU estimates used process user+system time sampled about every 0.5 seconds. Phase-boundary offsets reached 0.25 seconds on X60 and 0.47 seconds on x86. Accumulated CPU-quota throttled time was below 0.1 seconds in each roughly 15-second routed phase.
- x86 routed throughput at concurrency 4 ranged from 6,024 to 10,688 requests/s; at concurrency 64 it ranged from 10,339 to 10,509. The cause of this variation was not profiled.

</details>

### Timing the internal routing stage

The Router reports its internal routing interval in `x-vsr-routing-latency-ms`. Every timed routed response contained a valid value.

| Host | Concurrency | Internal routing p50 (ms) | Internal routing p95 (ms) |
| --- | ---: | ---: | ---: |
| RISC-V / X60 | 1 | 2.540 | 3.119 |
| RISC-V / X60 | 4 | 2.741 | 6.384 |
| RISC-V / X60 | 16 | 2.785 | 17.284 |
| RISC-V / X60 | 64 | 2.850 | 66.078 |
| x86 / Ryzen 9 9950X | 1 | 0.066 | 0.094 |
| x86 / Ryzen 9 9950X | 4 | 0.061 | 0.162 |
| x86 / Ryzen 9 9950X | 16 | 0.059 | 0.209 |
| x86 / Ryzen 9 9950X | 64 | 0.061 | 0.284 |

The header measures wall-clock time from request-body processing to the routing timestamp before forwarding, including scheduling waits. It excludes other gateway work, backend waiting and response processing. The end-to-end table includes those costs plus client-side work; its percentiles cannot be subtracted to obtain a Router-only latency.

At concurrency 4 and above, the 9950X deployment delivered about 38–39 times the X60's routed throughput. Both Routers were close to their two-CPU quota. The hosts differ in core design, clock speed, cache and kernel; the ratio describes these two systems running this workload, rather than RISC-V and x86 processors in general.

### Reproducing the measurement

The accompanying [Go probe](/files/ospp-riscv64/go-router-probe/main.go) contains the client and backend. The [measurement script](/files/ospp-riscv64/run-go-probe.py) configures and starts them with the Router, samples CPU use and cleans up afterward.

Download the [benchmark kit](/files/ospp-riscv64/benchmark-kit.zip) for the probe, tests, measurement script and results summary.

From the directory containing the accompanying benchmark files, check out the tested source revision:

```bash
git clone --no-checkout https://github.com/LeON-Nie-code/semantic-router.git \
  semantic-router-benchmark
git -C semantic-router-benchmark checkout --detach \
  2e89999771dc3bb2458e1bc86ef00c4e918dd591
VSR_SOURCE=$(realpath semantic-router-benchmark)
```

On RISC-V, build `semantic-router-router:local` from that checkout with the native build commands above. On x86, use the attached image's amd64 build path instead:

```bash
docker buildx build --platform linux/amd64 --target vllm-sr-attached --load \
  -f "$VSR_SOURCE/tools/docker/Dockerfile.attached" \
  -t semantic-router-router:local "$VSR_SOURCE"
```

Then build and run the benchmark on each host:

```bash
(cd go-router-probe && CGO_ENABLED=0 go build -trimpath -o ./go-router-probe .)
VSR_BENCH_RESULTS=$(mktemp -d)
sudo python3 ./run-go-probe.py \
  --source "$VSR_SOURCE" \
  --helper "$PWD/go-router-probe/go-router-probe" \
  --image semantic-router-router:local \
  --seconds 15 --repeats 3 --concurrencies 1,4,16,64 \
  --output "$VSR_BENCH_RESULTS/run"
```

Use Go 1.25.14 and an image built from the pinned checkout. The script needs Docker access and permission to read container CPU counters, and uses host networking and temporary mounts. The [results summary](/files/ospp-riscv64/go-router-probe-summary.json) includes phase quantiles, repeated-run ranges and CPU estimates. These measurements use the accompanying Go tool, rather than the repository's Python `standalone_http.py` benchmark.

## Support status

The proposed [experimental support-matrix entry](https://github.com/LeON-Nie-code/semantic-router/blob/2e89999771dc3bb2458e1bc86ef00c4e918dd591/website/docs/installation/support-matrix.md#L104) covers the standalone Router build and the routing, buffered/SSE response and restart checks described here. Envoy + ExtProc, local model inference, Dashboard, CLI stack orchestration, Operator and Kubernetes deployment are outside this PR's scope. Optional cache, knowledge-base, storage and plugin integrations have not been comprehensively tested.

The port is tracked in [PR #5259](https://github.com/vllm-project/semantic-router/pull/5259) and [#5310](https://github.com/vllm-project/semantic-router/issues/5310). Official RISC-V image publication remains to be arranged; the commands above build a local image.
