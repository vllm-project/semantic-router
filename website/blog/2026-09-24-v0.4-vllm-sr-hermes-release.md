**915 commits. 127 contributors. 104 contributing to this repository for the first time.** That is the scale of vLLM Semantic Router v0.4, Hermes, since the v0.3.0 tag. These are human Git authors in the [September 23 release-candidate snapshot](https://github.com/vllm-project/semantic-router/commit/3448de83f), matched by name or email against prior history with bots excluded. We will refresh the counts at the release tag.

The payoff is a simpler contract for applications: **one stable model name while the system chooses, delivers, and measures the right model behind it.** A smaller model may handle routine questions; a stronger one may earn its cost on difficult work; another may be needed for images, privacy, or a long agent session. Operators connect a qualified pool, publish a Mixture-of-Models (MoM) recipe, see why it chose a path, and compare that path with alternatives on the same tasks.

[Themis (v0.3)](/blog/v0.3-vllm-sr-themis-release) made routing stateful and inspectable. Hermes turns that foundation into an open model system that can improve without asking every application to rebuild around the latest checkpoint. Our mission is to make independently served models useful as one dependable experience—and to make claims of improvement testable.

## Why Hermes?

Hermes is the messenger between an application's intent and the models able to serve it. That journey now has more than one decision point. The Router must understand the request, choose a qualified path, preserve an agent's continuity, deliver a response through the right protocol, and learn from a measured outcome.

Consider an app that requests *vllm-sr/mom-v1-flash*. It is asking for responsive conversation, not binding itself to a server or checkpoint. An operator assigns models to that recipe, checks its decisions with Preview, publishes the entrypoint, and sends a real request. The app can keep its model name while a reviewed recipe update changes the underlying choice. The [MoM V1 family](/docs/overview/mom-model-family) offers four other objectives—Balance, Cost, Accuracy, and Vault—each with its own policy and backend requirements.

| Workgroup | v0.3 foundation | Hermes highlights |
| --- | --- | --- |
| Developer Experience & Ecosystem | Canonical YAML, CLI, and Dashboard contract | Public agent installation flow, Model Hub, Podman setup, and seven Workgroup charters |
| Enterprise & Environment | Inspectable config and deployment paths | Management permissions and redaction, Dashboard request protections, per-stack credentials, and a support matrix |

| Evaluation & Quality | Replayable routing decisions | sr-bench on frozen tasks, holdout controls, shadow exports, and separate Index and Arena evidence |

Each Workgroup owns part of the route from first setup to measured result.

## Seven directions, one routed experience

### Developer Experience & Ecosystem: make the first route understandable

A first request is useful only when a developer can explain what happened. In Themis, CLI, Dashboard, and YAML began to share one configuration contract. Hermes connects the next steps: discover the running Router's schema and operations, attach a model endpoint, inspect a recipe, preview the decision, then test an actual response. The [public agent installation Skill](/docs/installation/agent) follows that sequence and leaves the active revision and test evidence for review. It uses the same interfaces a human operator uses; an agent does not need a hidden setup path.

The [unified model catalog and Model Hub](https://github.com/vllm-project/semantic-router/pull/3489) make model cards and provider choices easier to discover; a catalog card is still no substitute for checking a live endpoint. The Dashboard brings the product objects together. In **Build → Models**, a developer can connect and verify a provider endpoint. **Mixture-of-Models → Recipes** shows the policy without embedding credentials in it. Publishing assigns connected models to decisions and exposes an entrypoint. Playground then shows the selected decision, algorithm, model, and response timing. The [Models, Entrypoints, and Serving guide](/docs/tutorials/global/models-entrypoints-serving) walks through that complete path.

Hermes also broadens the local starting point: [Podman is an explicit installer option](https://github.com/vllm-project/semantic-router/pull/3443). The important distinction during setup is simple. **Preview checks routing without generating an answer; Probe checks delivery through a real backend.** A team can see whether a poor result came from its policy or from the model endpoint before changing either.

*One path from setup to a request whose route can be explained.*

### Enterprise & Environment: give operators control over change

A better recipe must be safe to activate. Hermes strengthens the management boundary around a Router that can inspect prompts, choose providers, and change traffic. [Management API hardening](https://github.com/vllm-project/semantic-router/pull/2561) adds route-level permission checks, identity handling, and sensitive-field redaction. [Dashboard CSRF and origin checks](https://github.com/vllm-project/semantic-router/pull/2962) protect cookie-authenticated writes. These controls apply in their configured trust boundary; a local loopback setup can still run with management authentication disabled, so production access must be configured and reviewed.

The local stack now generates separate credentials for its managed data services [per stack](https://github.com/vllm-project/semantic-router/pull/2983), rather than relying on a shared default. For recipe changes, the [management API](/docs/tutorials/global/recipes) validates the full configuration, requires an ETag precondition, writes atomically with a backup, and exposes the active hash after activation. That gives an operator a concrete way to catch stale edits and verify what actually went live.

The [deployment support matrix](/docs/installation/support-matrix) says which Docker, Helm, Operator, gateway, and hardware paths the project maintains and how each is checked. It makes the distinction between a maintained stack, a supported integration, and an experimental example visible before someone builds on it. The aim is straightforward: teams should know which parts of a deployment are owned by the Router, which belong to their infrastructure, and what they need to verify before rollout.

![Protected management and deployment controls surrounding a versioned routing recipe](/img/blog/vllm/2026-09-24-v0.4-hermes-release/enterprise-environment.png)

*A policy change is useful when its access, activation, and deployment state can be checked.*

### Router Models & Inference Runtime: improve what the Router understands

The models that answer users are only half of a MoM. Small Router Models supply the evidence that guides each choice: subject, safety risk, personal information, semantic similarity, retrieval relevance, and more. [Vela 1.0](/blog/vela-models) releases fourteen open checkpoints across those tasks and text, image, and audio understanding. In its published selected evaluations, Vela Domain reaches **85.15 macro F1 across six languages**, compared with **66.33** for the preceding model. That is useful evidence for one task, not a claim that every route improves automatically.

The Router registry includes the Vela encoder base and ten task models. Later work puts **Vela Halu into a reference configuration** for answer-support detection and offers **opt-in native Omni execution** for text, image, and audio embeddings ([implementation](https://github.com/vllm-project/semantic-router/commit/1b77b8e55)). These are distinct from default behavior: Halu is a reference choice, and Omni requires an explicit multimodal deployment. Operators still select input budgets, artifacts, and devices for their workload.

Hermes also makes the execution of Router Models more deliberate. A [shared resource inventory](https://github.com/vllm-project/semantic-router/pull/3863) lets recipes and services reuse a physical model without hiding who consumes it; [optional admission controls](https://github.com/vllm-project/semantic-router/pull/3268) bound concurrent inference and queues. OpenVINO, Apple Metal, and RISC-V CPU paths have advanced on their stated model and hardware surfaces, with qualification described in the support matrix. Separately, the six open [Decision 1.0](/blog/decision-models) models explore a general decision layer. **Native integration of Decision into the Router remains a next step.**

![Router Models turn request content into typed evidence before a recipe chooses a backend](/img/blog/vllm/2026-09-24-v0.4-hermes-release/router-models.png)

*Better signals give a policy better evidence; measured outcomes show whether the choice helped.*

### MoM & Routing: turn a model pool into a product

Themis could match a decision and select a backend. Hermes gives that behavior a durable name. A public [entrypoint resolves to one isolated recipe](/docs/tutorials/global/entrypoints-and-recipes), whose signals, projections, decisions, selection logic, plugins, and state belong to that policy. Recipes can share physical model endpoints and Router Model assets without mixing their policy names or routing traces. An application asks for an objective; operators can revise the implementation behind it.

The five managed [MoM V1 recipes](/docs/overview/mom-model-family) show why that matters. **Blend** balances everyday quality, latency, and cost. **Lite** looks for economical service with targeted escalation. **Flash** favors responsiveness. **Ultra** keeps stronger answers and explicit review paths available. **Vault** applies a privacy-oriented policy, but its name cannot establish where an assigned provider stores or processes data; operators must choose backends that meet their requirements. None of the recipes supplies a magically qualified pool. Teams connect models, declare capabilities and context limits, and verify the chosen route.

For work that justifies more computation, [Fusion](/blog/vllm-sr-fusion-api) can compare or combine models rather than always selecting one. Hermes adds recipe-controlled analysis modes, a minimum number of valid responses, and a quorum-failure policy ([modes](https://github.com/vllm-project/semantic-router/pull/3635), [fallback](https://github.com/vllm-project/semantic-router/pull/3405)). Most requests can remain on a direct path. Decision ranking now keeps [tier and priority](https://github.com/vllm-project/semantic-router/pull/3974) distinct from [comparable measured confidence](https://github.com/vllm-project/semantic-router/pull/3959); [Preview explains](https://github.com/vllm-project/semantic-router/pull/3975) why one matched decision won. That matters when a safety route, a catch-all, and a model-scored route could all match the same request.

![A virtual model recipe selects or coordinates qualified backends according to its objective](/img/blog/vllm/2026-09-24-v0.4-hermes-release/mom-routing.png)

*The public name stays stable while the recipe makes the work and tradeoffs explicit.*

### Agentic & Context: keep long work coherent

An agent session is a sequence, not a stack of unrelated prompts. Themis introduced Session-Aware Agentic Routing to protect tool loops and provider continuations from unsafe model switches. Hermes builds around that foundation. An [ordered, request-owned context transformation plan](https://github.com/vllm-project/semantic-router/pull/3521) gives the existing compression and pruning steps a defined order, with protection for important instructions and tool exchanges. It does not silently enable a new transformation policy.

[Router Memory](https://github.com/vllm-project/semantic-router/pull/3483) can now extract useful facts from the response side and record bounded persistence receipts. Those receipts say what happened to a write, including failures or drops; storage is asynchronous and a request can continue when it cannot persist. For a long-running assistant, that distinction matters. “The answer was delivered” and “the memory was stored” are different outcomes.

The optional [recent-outcome switch gate](https://github.com/vllm-project/semantic-router/pull/3436) takes a bounded window of session evidence into account before accepting a proposed model switch. Cooldown and oscillation checks help keep one noisy turn from moving an agent back and forth. The gate is **off by default** and cannot override hard candidate eligibility. External agent runtimes remain responsible for the broader agent lifecycle; the Router provides bounded workflows, continuity, and switching contracts they can rely on.

![A long agent session retains important context while memory and model switching stay bounded](/img/blog/vllm/2026-09-24-v0.4-hermes-release/agentic-context.png)

*The Router can preserve the right context and explain when a session stays or switches.*

### Data Plane & Networking: deliver the choice

Once a route is selected, the request still has to reach a real endpoint and return in the format the client expects. Hermes puts OpenAI Chat Completions, OpenAI Responses, and Anthropic Messages through a more unified [protocol-neutral codec](https://github.com/vllm-project/semantic-router/pull/3076). The [compatibility matrix](/docs/installation/protocol-compatibility) covers buffered and streaming paths in both directions. Shared features translate; an unsupported target-specific feature returns a typed error rather than disappearing silently.

The path also understands a new kind of work. [Capability-driven image generation](https://github.com/vllm-project/semantic-router/pull/3313) can route a request to an image-capable model and translate the DALL-E images contract. A text backend is no longer assumed to be the right destination merely because it is available. Backend capability and real endpoint behavior still need to be verified before adding a model to a pool.

For upstream failures, an operator can enable [bounded fallback](https://github.com/vllm-project/semantic-router/pull/3937) within a recipe. It considers only eligible candidates, respects the remaining deadline, and avoids retrying after a stream is committed or a non-idempotent tool may have run. It is **disabled by default**. Together with clearer response-path and cost/latency headers, these boundaries let an operator tell which model actually delivered the answer, including when the first attempt did not.

![A selected route crosses protocol translation, backend dispatch, and the response stream](/img/blog/vllm/2026-09-24-v0.4-hermes-release/data-plane.png)

*The route has to hold through protocol translation, failure, streaming, and final delivery.*

### Evaluation & Quality: earn the right to call a route better

Themis made a routing decision replayable. Hermes gives teams a way to compare its outcome. [sr-bench 1.0](/docs/benchmarking/sr-bench) replaces the earlier evaluation surface with one durable service shared by CLI and Dashboard. It runs a MoM entrypoint and individual models against the **same frozen tasks**, then keeps results, run identity, capability measures, cost, latency, and token use together. Its adapters span knowledge, reasoning, coding, factuality, and agent work; a routed policy must be evaluated through the endpoint users will actually call.

The development and holdout boundary is deliberate. Quick slices help tune a recipe. Standard profiles use disjoint tasks, and a [frozen history snapshot](https://github.com/vllm-project/semantic-router/pull/3982) can exclude earlier evaluation membership before reserving a holdout. Replay can also yield a [reproducible shadow comparison dataset](https://github.com/vllm-project/semantic-router/pull/3998) for later analysis; exporting examples does not score answer quality by itself. These contracts make a measured gain more credible and make a regression easier to reproduce.

The [Open Intelligence Index and Arena](/docs/benchmarking/open-intelligence-index) serve a different purpose: they organize published, versioned catalog evidence across models and reveal missing benchmark coverage. A catalog score is not a fresh measurement of a deployment's MoM. sr-bench provides that live comparison. Hermes supplies the loop from proposal to evidence; a recipe advances when a representative holdout supports the change, with its cost and latency beside quality.

![Frozen tasks compare a routed Mixture-of-Models with individual models across quality, cost, and latency](/img/blog/vllm/2026-09-24-v0.4-hermes-release/evaluation-quality.png)

*The same work, measured through the real route, makes an improvement claim testable.*

## Workgroups are part of the release

This release also changes how the project organizes the work. [Seven public Workgroups](/blog/join-vllm-sr-workgroups) give long-lived technical directions a charter and an Epic owner. A request crosses their boundaries in practice: a developer publishes an entrypoint; a Router Model produces evidence; a recipe chooses a path; context and the data plane carry it; evaluation measures the result. Workgroup ownership makes the interfaces between those responsibilities easier to discuss and review.

![Seven Workgroups with clear ownership contribute to one routed application experience](/img/blog/vllm/2026-09-24-v0.4-hermes-release/workgroups-mechanism.png)

*Seven technical homes contribute to one path from request to measured outcome.*

A Workgroup is a technical home, not a permission level. A contributor can choose a charter, claim an available issue through its actual assignee state, deliver a focused PR, and join the Member roster after a reviewed roster PR. Public weekly issues keep useful starting points visible. Leads maintain their direction and help turn Epics into work others can pick up; the Open Source Team retains final acceptance, merge, role, and release authority.

That mechanism matters to the product. Improving a Router Model is only useful when it fits the runtime; a new algorithm needs a reliable transport and a fair test; a deployment improvement needs a clear operator contract. The Workgroups give those dependencies people and places to meet in the open.

## Start with one model name

After the v0.4 artifacts are published, install the CLI and start a local stack:

    curl -fsSL https://vllm-sr.ai/install.sh | bash
    vllm-sr serve

In the Dashboard, connect and verify your own model endpoints under **Build → Models**. Choose a MoM V1 recipe, assign models to its decisions, and publish an entrypoint. If you prefer YAML, the [recipe and entrypoint guide](/docs/tutorials/global/entrypoints-and-recipes) describes the same contract. Check each model's capabilities, context limit, and credentials before it takes traffic.

Use **Preview** to see which signals, decision, and model the policy selects. Then send a real request through Playground or [Route Probe](/docs/installation/agent) to verify backend delivery. Once you have a baseline and a candidate recipe, compare them with [sr-bench](/docs/benchmarking/sr-bench) on frozen tasks; keep development work separate from the holdout used for a public claim. The [MoM guide](/docs/overview/mom-model-family) covers the five built-in objectives and their assignment requirements.

## What comes next

We want an open model system that can improve as models, workloads, and evidence change. Hermes gives that work stable public names, isolated recipes, owned Router Models, explicit delivery contracts, and shared evaluation. Native Decision-model integration and reviewed recipe-tuning workflows are directions ahead. Each change will still need representative measurements, a reviewable policy revision, and a way back if the result disappoints.

Thank you to the contributors, Workgroup Leads and Members, reviewers, and users who built this release. [Find your Workgroup](/blog/join-vllm-sr-workgroups), bring a real problem, and help test the next answer. One model name can now carry a system behind it—and a community equipped to make that system better.
