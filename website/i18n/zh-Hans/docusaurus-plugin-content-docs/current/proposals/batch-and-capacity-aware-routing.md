# 路由范围：为什么路由器坚持逐查询，以及容量应归属何处

**版本：** 1.0
**作者：** vLLM Semantic Router 团队
**状态：** 决策记录

## 摘要

一个反复出现的问题是，语义路由器是否应该采用**批次级容量感知路由**：在共享成本预算和每个模型的并发限制下，将一整批并发查询联合分配给各个模型，正如近期的大语言模型路由研究（例如 *Robust Batch-Level Query Routing for LLMs under Cost and Capacity Constraints*）所提出的那样。本文档记录了为什么我们**不会**将批次级或容量感知优化纳入路由决策，而是让路由器保持**逐查询**，并将容量作为路由之下的**负载均衡职责**来处理。简而言之：路由器已经获得了真正重要的价值（近乎同等质量下的成本节省）；在我们自己的测量中，批次/容量方面的提升空间很小且不稳定；为实现清晰的关注点分离，容量控制应归属于服务/负载均衡层。

## 1. 路由器如今做什么（以及为什么这是正确的做法）

语义路由器是一个**逐查询分类网关**。对于每个请求，它根据提示词预测模型池中哪个模型是最佳目标，并转发该请求。这是在 Envoy `ext_proc` 热路径上进行的一次亚毫秒级决策。

它所提供的价值主张是**以近乎同等的质量节省成本**：将简单查询路由到低成本模型，将困难查询路由到能力更强的模型，从而让模型池以一小部分成本达到强大单一模型的质量。在一个公开的多任务路由基准测试（RouterBench，包含 11 个模型）上，经过无泄漏训练的逐查询路由器只需付出很小的质量代价，就能实现可观的成本节省：

| 保留的质量（相对于最佳单一模型） | 相对于最佳单一模型的成本 | 节省 |
| --- | --- | --- |
| 99%（−0.8 分） | ~55% | **~45%** |
| 98%（−1.6 分） | ~32% | **~68%** |
| 95% | ~19% | ~81% |

*（经过训练的梯度提升式逐模型质量估计器；随机行拆分；路由器在无法访问测试标签的情况下选择目标。绝对数值取决于模型池和估计器，参见 §4。）*

这才是合理的路由器价值主张：**用不到一个质量分数的代价换取大幅成本节省**。它完全是一种**逐查询**效应，既不需要批处理，也不需要容量模型。

## 2. 批次级容量感知路由会增加什么

该研究提案将路由重新表述为逐批次约束优化。它不再独立地为每个查询选择模型，而是接收**一批 N 个并发查询**，然后求解一项分配方案，在以下约束下最大化预测总质量：

- 整个批次共用的**共享成本预算**；以及
- **每个模型的容量限制**（一个模型实例最多可以服务的并发查询数）。

与逐查询路由相比，其声称的优势是在**非均匀或对抗性批次**（大量困难/昂贵查询同时到达）下表现更好；此外还有一种稳健变体，它使用预测质量区间的下界来对冲估计误差。

如果我们将来真的推进这一方向，合理的设计也**不会**在热路径上放置求解器。它会采用如下形态：路由仍然逐查询并保持快速；容量则位于独立的负载均衡层，路由器只是*感知*它：

```
                    ┌─────────────────────────────────────────┐
   request ───────► │  Semantic Router (ext_proc, per-query)   │
                    │  prompt → predict best model → target     │
                    └───────────────┬───────────────────────────┘
                                    │ target model (+ fallbacks)
                                    ▼
                    ┌─────────────────────────────────────────┐
                    │  Capacity / Load-Balancing layer          │
                    │  • per-model concurrency & queue depth    │
                    │  • least-loaded / spillover / admission   │
                    │  • fleet sizing (see fleet-sim)           │
                    └───────────────┬───────────────────────────┘
                                    ▼
                         backend model instances (GPUs / APIs)
```

在这种形态下，**容量是服务层职责，而不是路由职责**：路由器输出首选模型（以及按顺序排列的回退模型）；负载均衡层遵守实时并发限制，在模型池饱和时进行溢出转移，并由 [fleet simulator](../fleet-sim/overview) 离线确定规模。只有对**批量/异步**工作负载而言，批次级*联合*优化才可能合理；交互式流量绝不适用。

## 3. 为什么我们不把它纳入路由决策

### 3.1 与热路径冲突

路由器按请求工作，延迟低于一毫秒。批次级分配需要收集 N 个并发查询，并为每个批次求解一个整数/约束规划问题。将它嫁接到 `ext_proc` 上，会把快速、无状态的分类器变成一个依赖批处理和求解器的组件，破坏路由器得以作为内联式网关部署的关键属性。

### 3.2 测得的提升空间很小，而且很容易成为假象

我们在 RouterBench 上复现了批次级与逐查询路由的对比。乍看之下，在对抗性批处理下，批次级路由似乎远胜逐查询路由，领先 **+12 到 +16 分**。**这个差距是一个核算假象。** 它出现的唯一原因是批次级方案获得了*更大的总预算*：逐批次预算被设置为最昂贵批次的成本，并应用于每一个批次，导致批次级方案的总支出可以多出 **1.3×–6.2×**。当两种方案被限制在**相同的总支出**时，差距便大幅缩小：

| 批处理方式 | 预算比率（批次级/逐查询） | 朴素差距 | **总成本匹配后的差距** |
| --- | --- | --- | --- |
| 随机 | 1.1–1.4× | +1.2 到 +2.4 分 | **−0.2 到 −0.1 分** |
| 对抗性 | 2.1–6.2× | +12 到 +16 分 | **+0.1 到 +0.5 分** |

在成本相同时，批次级联合路由相对于逐查询路由带来的收益**≈0**。所谓“对抗性场景大获全胜”，实际上只是“对抗性批次集中了成本 → 逐批次预算更高 → 批次级方案可以花更多钱”。

### 3.3 容量耦合只有在约束很强时才有帮助，而且很脆弱

批次级分配*能够*优于贪心逐查询路由的一种情况，是**每个模型的容量形成约束**：优秀模型的槽位稀缺，因此联合分配可以把它们分给最需要的查询，而贪心的先到先服务路由会浪费这些槽位。我们准确测量了这一点：这种效应确实存在，但幅度很小，并且在成本压力下会发生反转：

| 场景 | 批次级 − 贪心（准确率） |
| --- | --- |
| 容量不构成约束（对照组） | −0.1 分（≈0，符合预期） |
| 容量构成中等约束 | +0.3 分 |
| 容量构成严格约束 | **+1.2 分** |
| 容量构成约束 **+ 成本压力** | **−1.2 到 −3.4 分** |

因此，这种耦合在最佳情况下（容量严格受限且没有成本压力）能带来约 1 分的收益，但一旦同时施加成本压力，收益就会**转为负值**。这样的收益不够稳定，不足以证明在路由路径上放置求解器是合理的。

### 3.4 关注点分离

实时容量，包括并发限制、队列深度、饱和度和溢出转移，是一种**服务层**属性；它每秒都在变化，并且取决于部署所使用的硬件。它最适合由负载均衡和准入控制处理，并由舰队模拟器离线确定规模。将其编码到语义路由决策中，会把一种缓慢变化、由语义驱动的选择（哪个模型对这个提示词而言是*合适的*）与一种快速变化、由基础设施驱动的选择（哪个实例有一个*空闲槽位*）耦合起来。将二者分开，可以让路由器保持简单、快速，并能跨部署移植。

## 4. 测量结果的客观局限

- **基准测试，而非生产流量。** RouterBench 采用类似多项选择题的任务，以 0/1 表示正确性。真实流量是开放式的，其中“哪个低成本模型也能给出正确答案”更难定义和标注。对于 §1 所述的逐查询价值主张，真正的瓶颈是从实时流量中获得可靠的逐模型质量标签，而不是路由算法。
- **依赖估计器。** §1 中的成本节省前沿取决于质量估计器。在相同特征上，更强的估计器相较于较弱的估计器，能让近乎同等质量下的节省大致翻倍（在 99% 质量时从 17% 提升到 45%）。值得追求的提升空间在于**估计器**，而不在批次/容量优化。
- **无法与最佳单一模型的质量完全相同。** 当一个模型在困难查询上占据优势时，无论成本多少，都没有路由器能达到其 100% 的质量；价值在于近乎同等质量的权衡，而不是严格超越最佳模型。
- **运行点。** 在生产环境中，应在验证集拆分上调优成本控制参数（λ），而不是在评估集上调优。

## 5. 决策

- **保持逐查询路由。** 它能在热路径上获得真实且可观的价值（近乎同等质量下的成本节省）。
- **不要将批次级或容量感知优化纳入路由决策。** 相比总成本匹配的逐查询路由，测得的提升空间为 ≈0（批次级）到约 1 分（容量严格受限），并且在成本压力下并不稳定。
- **将容量作为路由之下的负载均衡层来处理**（最小负载/溢出转移/准入），并由 [fleet simulator](../fleet-sim/overview) 确定规模。路由器可以输出按顺序排列的回退模型供负载均衡层使用，但自身不求解容量约束优化问题。
- **改为投资质量估计器**，因为剩余的成本节省空间就存在于此。

## 6. 何时重新审视

如果满足以下任一条件，就应重新审视此决策：容量在生产环境中确实成为严格约束（稀缺的优秀模型槽位主导了成本状况）；新增了一条专用的**批量/异步**路由路径，且该路径可以接受逐批次求解延迟；或者逐查询质量估计器足够强，使剩余的提升空间明确地从估计转移到了分配。
