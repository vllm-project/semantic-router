# 为何需要语义路由 {#why-semantic-routing}

模型在推理能力、速度、价格、上下文长度、模态、工具、位置和安全性上各不相同，模型池也会随每次升级或故障而变化。Semantic Router 为 harness 提供一个稳定的模型 API，并把模型选择变成一条可阅读、可测试、可修改的策略。

- **一个稳定的 API。** Harness 调用公开模型名；运维人员可以随时更换背后的模型池。
- **硬性规则优先。** 身份、数据位置、模态和上下文上限会先排除不合格的模型，再比较成本或延迟。
- **用自然语言做判断。** 一个决策模型回答策略针对每个请求提出的问题，因此规则读起来是问题，而不是代码。
- **可度量的变更。** 回放、评估和指标会告诉你一次策略变更是否有效。

## 它解决的问题 {#the-problems-it-solves}

| 问题 | 没有路由层时 | 使用 Semantic Router 时 |
| --- | --- | --- |
| **模型选择与 harness 耦合** | 每个集成都写死自己的模型。 | 公开入口把 harness 调用的名字与背后的模型解耦。 |
| **约束与偏好混在一起** | 便宜的模型即使不被允许也可能胜出。 | 决策先排除无效路径，算法只对剩余候选排序。 |
| **一条规则不够用** | 关键词抓不住意图，模型的猜测还可能越过授权规则。 | 信号把各类证据分开，决策再把它们组合起来。 |
| **模型池不断变化** | 升级、扩缩容和故障会破坏路由代码。 | 健康状态、延迟和负载参与选择，但不会取代策略。 |
| **有些回答需要多个模型** | 升级和评审只是临时的重试。 | 逐级升级和编排是路由中明确、有界的步骤。 |

路由既是语义问题，也是系统问题。请求说明工作需要什么，模型池说明有什么可用。Router 把两种视角结合起来，但不让任何一方单独成为全部策略。

## 设计目标 {#design-goals}

1. **在众多后端之上提供一个稳定的 API。** Harness 使用公开入口，运维人员管理背后的模型池。
2. **策略可阅读、可测试。** 信号、投影、决策、算法和插件都是具名配置对象，而不是散落各处的条件判断。
3. **先划硬边界，再做优化。** 在质量、延迟、成本或负载影响选择之前，先移除不合格的路由。
4. **模型选择与有界协作。** 一条路由可以选择一个模型、逐级升级、比较，或在配置的限制内协调多个模型。
5. **运维反馈。** 回放、评估、指标和用户反馈支撑有依据的策略变更。

## Semantic Router 不是什么 {#what-semantic-router-is-not}

- **不是 agent harness。** Harness 负责任务循环、工具执行和任务状态；Router 决定每一次模型调用。
- **不是对话模型服务器。** 回答由 vLLM、Ollama 或托管提供方生成。内置模型运行时只服务 Router 自己的决策模型和嵌入模型。
- **不只是负载均衡器。** 副本健康固然重要，但哪个模型池合格由请求含义和策略决定。
- **不保证质量。** 路由效果取决于所配置的模型、信号、策略和评估数据。
- **不是安全边界。** 它在由网络、身份和数据治理控制构成的整体架构中执行路由策略。

:::tip 不接对话后端也能提供决策
应用也可以通过 [System One](../system-one/overview) API 直接向决策模型提问。
:::
