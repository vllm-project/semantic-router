# Reproducing the Jev research

Local preparation for issue #3970, not an approved shared protocol or evidence
of a completed pilot. Mock checks validate the harness; they do not measure Jev.

## 1. Reproduce the offline checks

Obtain the exact source and fixtures, install the repository's Go/build
dependencies, then run from the repository root:

```bash
make test-jev-eval
make vet-jev-eval
```

Tests need permission to bind local loopback HTTP ports. They do not require a
Jev key, model downloads, or paid calls. Initial Go dependency installation may
require network access. Passing means the tested harness behaviors match their
assertions, not that a real provider or production Router was evaluated.

## 2. Share enough material to inspect a real run

Include these together; hashes identify files but cannot replace their contents:

- Exact runner source: preferably an accessible clean commit. For a dirty run,
  also supply the tracked patch and all required untracked source/fixture files.
  A commit hash or `git diff` alone does not capture those untracked files.
- Exact input JSONL and question JSON. For this Jev draft, the question contains
  the label mapping/descriptions; no separate mapping file is consumed.
- Original result JSONL, including failed and not-executed cases, plus the
  completed run manifest below. Review provider bodies for sensitive data
  before sharing; never include API keys, authorization headers or environment dumps.

The current shared-pilot inputs are `pilot-v0.1/inputs.jsonl` and
`pilot-v0.1/question.json`, relative to this directory. Start with
[the pilot workspace](pilot-v0.1/README.md). Earlier `testdata/shared-pilot.*`
drafts are historical fixtures; do not use them as the current collaboration entry.

## 3. Small run manifest template (manual, not generated by the runner)

Copy this alongside a future result file and fill the nulls from that actual
run. Null means not recorded yet, never zero. This is a local draft format, not
an agreed cross-model schema. Do not describe the current dirty checkout using
only its base commit, and do not mark a mock run as a live run.

Record `mode` as `live` only for real provider calls; set `status` to `completed`
or `stopped` afterward. The manifest is descriptive: the current runner neither
reads it nor verifies `--revision`. Record the actual flags and any deviations.
The fail-fast policy is the current Jev harness behavior, not an agreed policy
for all three arms. Request-wall time is not provider-only inference time.

## 4. What another contributor can verify

For a local, read-only Markdown view of the native records:

```bash
python3 bench/jev/report.py bench/jev/testdata/report.mock.jsonl --mode mock
python3 -m unittest discover -s bench/jev -p 'test_report.py' -v
```

The four-row mock file is hand-authored, reduced demonstration data with
placeholder metadata and two labels. It is not a capture from Jev, not the
six-case pilot, and not a complete run artifact. For real native records, pass
their file path and `--mode live`; mode is an operator declaration, not verified
provenance. Output goes to stdout; no files are overwritten or API calls made.
The table keeps source line references and the source file hash, distinguishes
unscored/failed/unexecuted rows, and refuses duplicate IDs or mixed source hashes.
It trusts recorded contract outcomes, does not recompute probabilities, and
does not establish complete case coverage. It is not a shared-schema exporter,
aggregate scorer, or three-arm comparison. Keep the original JSONL and manifest.

1. Recompute SHA-256 of the supplied files and compare input/question hashes
   against those in the case records. Match source artifacts to the manifest.
2. Check every planned case ID is accounted for. Distinguish attempted records
   from `jev-research-not-executed.v1`; missing cases may mean an incomplete file.
3. Inspect preserved responses and check contract/scoring against the same
   question and expected labels. This is currently manual: no offline replay
   CLI or shared-schema exporter has been implemented.
4. If rerunning live later, use an independently authorized key and budget.
   Repeating the procedure does not guarantee identical remote predictions,
   latency or cost. Do not overwrite or merge separate runs silently.

Before comparing Jev/Kai/Vela, verify the agreed cases, label meanings, versions,
scoring and failure policy, and identify differing timing boundaries. A complete
manifest makes differences inspectable; it does not make unlike runs comparable.
